- Подготовлен защищённый пошаговый runbook (создание роли/базы со случайным
  паролем, `listen_addresses`, `pg_hba` hostssl только для `kniga`, рестарт,
  запись строки подключения в root-only файл на сервере).
- **Статус: готово.** PostgreSQL 14 на сервере, отдельная база/роль `kniga`,
  внешний доступ по TLS + scram. В Render задан `DATABASE_URL` (Secret) — сервис
  пересобрался на постоянную БД.
- **Проверено вживую:** `/api/health` → 200; в Postgres создались все таблицы
  приложения (вкл. колонку `ui_mode`); dev-login через живой сайт создал запись,
  которая видна прямым запросом к Postgres, → данные переживают редеплой.
  Тестовый аккаунт удалён, прод чист.
- Безопасность: доступ к серверу выдавался в переписке — по завершении сменить
  root-пароль; для интерима БД слушает 5432 (защита TLS + scram + случайный
  пароль), при переезде сайта на этот сервер порт закрыть и ходить по localhost.

## Постоянная БД: код готов к PostgreSQL · 2026-08-18

Приложение переведено на подключение к внешнему Postgres по `DATABASE_URL`
(SQLite остаётся дефолтом для локалки и тестов). Размещение БД решается отдельно
и **не требует доменного имени** — БД подключается по host:port, это не переезд
сайта.

- `requirements.txt`: драйвер `psycopg[binary]` (локально не нужен — SQLite).
- `config.py`: `database_url` (env `DATABASE_URL`) + `effective_db_url`
  (приоритет над `db_url`).
- `db.py`: нормализация `postgres://`/`postgresql://` → `postgresql+psycopg://`;
  для Postgres — `pool_pre_ping` + `pool_recycle=300`; мини-миграция колонок
  (ALTER ADD COLUMN) валидна и в PG.
- `render.yaml` + `.env.example`: переменная `DATABASE_URL` (Secret).
- Проверка: backend **94 passed** (тесты на своём in-memory SQLite, не затронуты);
  офлайн — `DATABASE_URL` перекрывает `db_url`, схема нормализуется в psycopg,
  диалект резолвится, `pre_ping` включён. Живой round-trip к PG отложен (локальный
  Docker-демон не запущен) — подтвердится на деплое после установки `DATABASE_URL`.
- Размещение (переходный период, сайт на Render) — на выбор владельца: Timeweb
  managed PG / Render PG / Neon / self-host на существующем VPS Timeweb.

## Два интерфейса — простой и продвинутый · 2026-08-18

По предложению Тани — два уровня интерфейса гадания, переключатель в личном
кабинете, по умолчанию **простой**.

- **Простой:** только режим «64 гексаграммы», без кнопки «Проверить вопрос»,
  готовые вопросы остаются. **Продвинутый:** текущий UI как есть (8/64/монеты +
  проверка). Предпочтение привязано к аккаунту + зеркалится в localStorage
  (`kn_ui_mode`); у анонимных гостей всегда простой.
- **Backend:** `User.ui_mode` (дефолт `simple`); идемпотентная мини-миграция в
  `db.py::init_db` (ALTER TABLE, т.к. SQLite `create_all` не добавляет колонки);
  `ProfileUpdateRequest.ui_mode`; `PATCH /auth/me` и `user_public` учитывают поле.
- **Frontend:** `App.tsx` читает `useAuth()` → `effectiveUiMode()` (аккаунт →
  кэш → simple), в простом форсит `mode="64"`, прячет `.mode-switch` и передаёт
  `showCheck={false}` в `QuestionInput`; карточка «Интерфейс» в `CabinetPage`
  (сегмент-переключатель через `updateProfile({ui_mode})`); кэш `ui_mode` в
  `auth.tsx`; демо (`demo.ts`) и типы обновлены.
- **Тесты:** backend `test_auth.py` — дефолт `simple`, `PATCH` на `advanced`,
  невалидное → 422 (**94 passed**). Frontend — pure-хелпер `lib/uiMode.ts` +
  4 юнит-теста (**vitest 17 passed**). tsc strict + прод- и демо-сборка зелёные.
- **Проверка вживую:** демо-сборка через `vite preview`, скриншоты обоих
  состояний (Chrome headless): простой — только выбор гексаграммы + пресеты, без
  переключателя и без «Проверить вопрос»; продвинутый (залогинен, `advanced`) —
  режимы 8/64/монеты + «Проверить вопрос» + символ дня.
- Довесок: выбор триграмм в гексаграмме (Нижняя/Верхняя) переведён на ровную
  сетку **4×2** (`.picker-choices` → grid вместо flex-wrap; на телефоне 2 колонки).
